# Token 统计探索与下一步建议

探索日期：2026-10-05。下文现场诊断记录探索时的状态；后续用户授权后，第一阶段已实现。遵循轨迹评审技能的原则：区分用量来源、保留未知和部分覆盖，避免重复计数。

## 第一阶段实现进展

已补齐逐字段完整性、完整 trace 填补缺失汇总、失败/取消/超时的可见消耗下界，以及独立用量摘要证据。案例、预算、运行指标、资源规则、Markdown/JSON/证据包与页面读取相同来源；按模型的部分用量也会保留。新增健康接口采集就绪检查和明确的离线模式提示。原有完整总量字段保留语义，下界保存于 `fields.*.value`，不把未知填零。

内置固定仓库配方仍只有 smolagents。后续新增 [Python LLM 自动适配](AUTO_ADAPTATION.zh-CN.md)，生成桥接入口并提供有限的 httpx/原生调用采集；这不等于第二、三阶段的全框架 SDK 接入和受控模型网关。其他框架仍可提供 `target-v1`、部署清单或通用轨迹转换器；历史缺失用量无法还原。实现合同和操作见 [调用记录指南](TARGET_TELEMETRY.zh-CN.md)。

## 当前数据链路

`模型响应 usage → 框架 token_usage → 适配器 trace/usage → TargetResponse 校验 → 案例 _usage → 网页/导出`

关键实现位置：

- `examples/smolagents/telemetry.py`：读取模型响应的 `token_usage`，保存每次调用用量。
- `examples/smolagents/agent_server.py`：在真实模型模式中汇总每轮实际调用；离线脚本模型不返回用量。
- `src/agent_trace_review/assessment_contracts.py`：校验自报用量；完整逐次记录可派生轮次汇总。
- `src/agent_trace_review/assessments.py`：案例和预算级汇总。
- `src/agent_trace_review/generic.py`、`analysis.py`：从独立 llm 事件计算运行轨迹指标。
- `web/src/assessments.tsx`：展示输入、输出、总 Token，缺失值显示未知。

已有 `tests/test_target_telemetry.py` 的 18 项测试本轮通过。它验证协议和归并，并不证明任意 Agent 已接入采集。

## 已确认的功能缺口

1. **默认离线模式的反馈不够明确。** 完整工具轨迹不代表 Token 完整；离线未执行模型应显示“不适用（离线校准）”，不能与真实调用缺失用量混在一起。
2. **依赖目标自报。** 核心评测服务只调用目标 `/task`，没有通用模型采集 SDK 或评审方控制的模型网关；已知源码扫描也无法还原一次运行中的全部模型请求。
3. **部分用量被整体隐藏。** `_usage` 要求执行完整且每轮都有用量。已完成调用记录 10 输入、5 输出、15 总 Token 后发生中断，当前案例汇总仍全部返回 null。预算级曲线也只有所有案例用量齐全时才给出总数。
4. **完整逐次记录未填齐部分轮次汇总。** 当目标顶层只提供 input=10，而完整 llm 事件提供 input=10、output=5、total=15，校验器检查一致性后仍留下 output/total=null；网页读取顶层派生案例汇总时继续显示未知。
5. **页面之间的用量来源不一致。** 主动评测页使用轮次汇总；运行详情的资源规则只从 llm 事件读取。目标仅给顶层汇总时，主动评测页可能有数字，而运行详情仍未知。需要显式支持“轮次汇总证据”，避免伪造模型事件。
6. **细分指标缺口。** 通用 Token 合约没有缓存命中/未命中字段，smolagents 采集也未保留推理 Token 细分。现有 OpenCode 分析虽有缓存指标，不能据此宣称主动评测已经支持。
7. **诊断缺失。** 缺少“未接入采集 / 供应商没返回 / 流结束前中断 / 部分调用缺失”等原因和逐字段覆盖率。

评审模型调用的 Token 存放在 LLM review 的评审元数据里，应和被测 Agent 的调用消耗分别展示。

## 采集路线比较

|路线|接入条件|可覆盖内容|工程代价与限制|
|---|---|---|---|
|框架/SDK 包装|可修改或包装被测源码的模型调用入口|每次调用用量、轮次关联；框架钩子还能采集工具|适合已知源码；需适配不同框架、流式和重试入口|
|评审方管理的模型网关|目标的模型地址可指向网关，模型请求实际经过网关|从供应商响应采集 Token，目标失败时也可保留外部用量|更适合比赛受控部署；多案例共享目标时，精确归属仍需可信任务关联上下文|
|已有 OpenTelemetry 轨迹接入|目标已有模型 span 或可加标准埋点|通用的调用、Token、子 Agent 层级|需要标准字段映射、接收/导入和任务绑定；不是无需埋点的自动采集|
|模型 tokenizer 估算|能拿到实际传给模型的消息、工具定义和输出，并匹配 tokenizer|估计用量|估计单列；外部任务问句/最终答案不足以估算内部全部调用|

DeepSeek Chat Completions 官方响应包含 `usage.prompt_tokens`、`completion_tokens`、`total_tokens` 及缓存/推理细分。流式使用方式应按当前官方文档读取末尾携带用量的 chunk，不能简单累加每个片段或只收集文本。[DeepSeek 官方协议](https://api-docs.deepseek.com/api/create-chat-completion/)

可复用 LiteLLM 作为模型网关：已有调用 Token 日志、虚拟凭据和 request_id 查询。虚拟凭据与持久化用量管理需要其数据库/部署配置；它不会自动生成本项目的 case_id/turn 关联。[用量日志](https://docs.litellm.ai/docs/proxy/cost_tracking)、[虚拟凭据](https://docs.litellm.ai/docs/proxy/virtual_keys)

OpenTelemetry 可作为后续互通协议，现有项目需接收和转换对应模型 span；GenAI 规范已迁移至单独仓库，接入时固定版本。[官方规范仓库](https://github.com/open-telemetry/semantic-conventions-genai)

## 建议的实现次序

### 第一阶段：补齐现有统计和运行前诊断

- 为每个 Token 字段增加完整性和原因：完整、部分、不适用、未知；页面显示完整数字或 `≥已观测值`，零与未知区分。
- 当完整逐次证据提供缺失字段时补齐轮次汇总；已提供字段发生冲突仍拒绝或明确标注冲突。
- 取消、失败、超时保留可见消耗，但不把部分消耗当作整个任务的完整总额。预算上限已被可见用量超出可判失败；可见用量未超出不能确认满足预算。
- 案例、预算、评测总览、运行详情和报告使用一致的用量汇总来源；顶层汇总不制造不存在的模型调用。
- 运行前展示真实/离线模式和采集就绪状态。已存在历史记录只展示其真实来源；缺少历史证据时无法恢复实际用量。

这是当前问题的最小有效范围，可以立即改善已有 Agent 和失败任务的可观测性。

### 第二阶段：增加通用采集入口

先提供 OpenAI 兼容/DeepSeek 响应的规范化函数和轻量模型包装，覆盖非流式、流式、重试及异常。输出仍接入现有 target-v1，保留模型标识、供应商请求 ID、调用 ID、输入/输出/总 Token，并按供应商定义保留缓存和推理细分。推理/缓存通常是输入或输出的细分，不重复加进总量。

对每次调用绑定 `assessment_id/case_id/budget_id/attempt/session_id/turn/call_id`。传给多层子 Agent 的上下文需要随调用传播；仅根据时间范围归属请求会在并发场景中混算。

### 第三阶段：比赛受控部署接入模型网关

建议试点复用 LiteLLM，与本项目的受控 Docker 部署结合。真实供应商凭据由网关管理，被测进程使用范围受限的凭据；每次请求由受信入口关联任务。一个凭据可先获得整场评测汇总，但要获得准确逐案例统计仍需最小适配器传播任务上下文，或使用互相隔离的案例执行环境。

网关采集仅覆盖实际经过网关的请求；若比赛要求禁止绕过，需在独立受控运行环境配置出站策略。Token 来源标记为网关采集的供应商报告，仍不宣称是已核对账单。

网关和目标可能同时报告同一调用：优先使用可关联的供应商请求 ID 归并不同证据；无法关联时选定单一统计来源并标注覆盖限制，避免两份数据直接相加。重试产生的新请求应分别记账，重复导入同一条记录应幂等。

### 验收条件

固定控制 API 返回每调用 10 输入、5 输出 Token，两次调用应得 20/10/30；两轮应得 40/20/60。另外覆盖：顶层汇总与逐次记录同时存在、只给汇总、部分字段、只给完整 trace、流式末尾 usage、取消/失败、重试、并发任务、重复导入、缓存/推理细分和评审模型的独立消耗。

真实 DeepSeek 小题验证应在用户决定执行阶段和调用范围后进行。此次探索仅只读本地记录与官方文档、运行本地测试和最小复现；没有新模型调用，也未修改本地 `.env`。
